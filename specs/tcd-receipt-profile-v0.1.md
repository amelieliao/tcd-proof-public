# TCD Receipt Profile v0.1

Status: Draft / Pilot

Profile: `illustrative_public_pilot_profile`

Signature algorithm: `Ed25519`

Runtime generated: `false`

Synthetic data: `true`

This profile defines a narrow public verifier contract for synthetic TCD Proof fixtures. It is designed to show how a selected AI-assisted action can be bound to policy, configuration, build/image context, evidence references, and verification status without exposing raw customer data.

This profile is not a production HSM deployment, not a hardware-rooted production signing profile, not global consensus, not regulatory certification, and not proof that an AI model was correct. It is also not currently integrated with the private TCD runtime HTTP receipt path.

## Scope

The v0.1 public profile covers:

- a synthetic receipt envelope;
- a receipt body with action, policy, build, image, config, and evidence references;
- an Ed25519 authenticity signature over canonical receipt-body bytes;
- expected binding checks performed by an independent verifier;
- stable failure codes for public verifier tests.

The profile intentionally excludes:

- raw customer data;
- raw documents;
- raw prompts;
- raw model answers;
- secrets or private signing material;
- private runtime source code;
- production KMS/HSM integration.

## Required Top-Level Fields

Each receipt fixture using this profile MUST include:

```json
{
  "schema": "tcd.receipt.profile.v0.1",
  "profile": "illustrative_public_pilot_profile",
  "profile_version": "0.1",
  "runtime_generated": false,
  "synthetic_data": true,
  "claim_status": "illustrative_verifier_test_vector",
  "receipt_ref": "receipt:synthetic:...",
  "receipt_body": {}
}
```

The `runtime_generated` and `synthetic_data` values are normative for this pilot profile. A receipt generated by another runtime or data profile MUST use a different profile or a later version.

## Canonicalization Boundary

The authenticity signature uses canonical JSON bytes generated from the receipt body after removing the entire `auth_sig` object. The v0.1 reference canonicalization is the concrete rule set defined in this repository; it should not be described as a general cross-language canonical JSON standard.

Canonical JSON serialization rules:

- UTF-8 bytes;
- stable JSON object ordering;
- `sort_keys=True`;
- compact separators equivalent to `(",", ":")`;
- `ensure_ascii=False`;
- `allow_nan=False`.
- no Unicode normalization;
- duplicate object keys are rejected during JSON parsing before canonicalization;
- `NaN`, `Infinity`, and `-Infinity` are rejected during JSON parsing before canonicalization.

JSON strings, booleans, null values, arrays, and nested objects are serialized according to the Python `json.dumps` settings above after strict parsing. Fields that are semantically integers, such as `v` and `ts_ns`, are represented as JSON integers. The v0.1 profile does not require floating-point or decimal fields; implementations should avoid adding them unless a later profile defines exact representation limits.

In Python terms, the signed bytes are:

```python
json.dumps(
    receipt_body_without_auth_sig,
    ensure_ascii=False,
    sort_keys=True,
    separators=(",", ":"),
    allow_nan=False,
).encode("utf-8")
```

Other language implementations must reproduce these v0.1 bytes exactly and verify compatibility with the published test vectors. A future profile may migrate to RFC 8785/JCS or another canonicalization standard, but it must do so under a new profile/version and must not silently change v0.1 signed bytes.

## Signature Semantics

The verifier MUST:

1. Load the Ed25519 public key supplied by the verifier caller.
2. Compute the public-key fingerprint as `sha256:` plus the SHA-256 hex digest of the DER SubjectPublicKeyInfo bytes.
3. Check that `receipt_body.auth_sig.alg` is `Ed25519`.
4. Check that `receipt_body.auth_sig.key_id` matches the expected key ID when an expected key ID is provided.
5. Check that `receipt_body.auth_sig.public_key_fingerprint` matches the supplied public key and any expected fingerprint.
6. Remove the entire `auth_sig` object from `receipt_body`.
7. Serialize the remaining receipt body using the canonicalization rules above.
8. Verify `receipt_body.auth_sig.val` as a base64 Ed25519 signature over those canonical bytes.

Detached fields such as `sig` or `receipt_sig`, when present in other receipt families, MUST NOT be described as this profile's public asymmetric signature. This profile's public authenticity signature is `receipt_body.auth_sig`.

The top-level transport wrapper, `receipt_body.auth_sig`, and binding objects reject unknown fields. If future fixture authors need extra signed material, they must place it under `receipt_body.extensions`; the entire `extensions` object is included in the canonical signed bytes.

## Expected Bindings

The verifier checks the signed receipt against an expected bindings document. Expected bindings MAY include:

- `key_id`;
- `public_key_fingerprint`;
- `policy_ref`;
- `policy_digest`;
- `build_id`;
- `image_digest`;
- `cfg_fp`;
- `service_config_fingerprint`;
- `required_fields`.

The signature can be valid while a binding check fails. For example, a verifier that supplies the wrong expected policy MUST receive `POLICY_BINDING_MISMATCH` even though the receipt signature itself is valid.

## Stable Failure Codes

The public verifier uses stable failure codes:

- `SCHEMA_INVALID`
- `UNSUPPORTED_PROFILE`
- `UNSUPPORTED_ALGORITHM`
- `SIGNATURE_INVALID`
- `KEY_ID_MISMATCH`
- `PUBLIC_KEY_FINGERPRINT_MISMATCH`
- `POLICY_BINDING_MISMATCH`
- `BUILD_BINDING_MISMATCH`
- `IMAGE_BINDING_MISMATCH`
- `CONFIG_BINDING_MISMATCH`
- `REQUIRED_FIELD_MISSING`
- `INVALID_JSON`
- `DUPLICATE_JSON_KEY`
- `NON_FINITE_JSON_NUMBER`

## Reconciliation Boundary

The reconciliation fixtures prove a completeness mechanism over synthetic input lists: an independent upstream eligible-action population is compared with receipt index rows and verification results.

This does not prove that a real customer workflow has no silent gaps. A production deployment would need an integration-specific upstream action source, controls that prevent bypass, durable storage guarantees, and operational monitoring.
